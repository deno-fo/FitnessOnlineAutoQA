# Требования к приложению для мобильных автотестов

## 1. Стабильные идентификаторы элементов

Для элементов, с которыми взаимодействуют автотесты, нужны стабильные идентификаторы:

- Android — `resource-id` или `content-desc`;
- iOS — `accessibilityIdentifier`.

Идентификаторы не должны зависеть от языка приложения, видимого текста или положения элемента на экране.

Сейчас часть кнопок, полей ввода, пунктов настроек, сообщений об ошибках и элементов выбора тренировок приходится искать по английскому тексту, типу элемента или XPath. Изменение текста, языка или структуры экрана может сломать такой тест, даже если сама функциональность продолжает работать.

## 2. Английская клавиатура для поля пароля на iOS

На реальном iPhone поле пароля использует последнюю выбранную пользователем раскладку. Если активна русская клавиатура, Appium не всегда может ввести пароль, состоящий из латинских символов.

Поле пароля нужно настроить как ASCII-capable, чтобы iOS автоматически открывала подходящую клавиатуру:

```swift
passwordField.keyboardType = .asciiCapable
```

## 3. Сброс состояния приложения на реальном iPhone

Существующая функция:

`More → Settings → Caching → Clear cache`

удаляет только загруженные видео, изображения и другие файлы кэша. Авторизация, настройки, онбординг и остальные локальные данные не сбрасываются. Поэтому простого удаления кэша недостаточно для подготовки приложения к автотесту.

На реальном iPhone Appium не может самостоятельно полностью очистить данные уже установленного приложения. Для отдельной QA-сборки нужно реализовать специальный сброс локального состояния.

Возможные способы вызова:

- специальный deep link, например `fitnessonline-qa://reset`;
- аргумент запуска, например `--reset-local-state`.

При вызове сброса приложение должно удалять:

- данные авторизации и токены из Keychain;
- локальную базу данных, если она используется;
- сохранённые настройки;
- признаки прохождения онбординга;
- информацию о ранее показанных подсказках;
- локальные файлы и кэш.

После сброса приложение должно открываться в таком же состоянии, как после первой установки.

Функция сброса должна присутствовать только в QA-сборке и быть недоступна в приложении для обычных пользователей.

## 4. Признак готовности интерфейса

Нужно реализовать однозначный признак того, что экран полностью загрузился и готов к взаимодействию.

Возможные варианты:

- элемент загрузки со стабильным идентификатором, например `screen_loading`, исчезает только после полной готовности экрана;
- кнопки и другие интерактивные элементы остаются в состоянии `disabled` и становятся `enabled` только после завершения загрузки;
- специальный элемент или атрибут `screen_ready` получает значение `true`, когда экран готов.

Предпочтительный вариант — использовать нормальное состояние загрузки и не активировать элементы управления до фактической готовности экрана. `screen_ready` можно использовать как отдельный признак для автотестов, если состояние интерфейса определить другим способом нельзя.

Дополнительно для QA-сборки можно добавить аргумент запуска, отключающий или сокращающий переходные анимации.

Сейчас некоторые элементы уже отображаются, но ещё не реагируют на нажатия. Из-за этого в тестах приходится использовать ожидания с запасом, которые увеличивают продолжительность тестов и не гарантируют их стабильность.

## 5. Всплывающие подсказки, блокирующие экран

Некоторые подсказки перекрывают весь экран. Пока такая подсказка открыта, Appium не может нажимать на элементы, расположенные на экране.

Это усложняет автотесты по следующим причинам:

- подсказка может появиться с задержкой уже после начала взаимодействия с экраном;
- изменение текста или структуры подсказки ломает логику её закрытия;
- один и тот же тест может пройти при одном запуске и упасть при следующем.

Возможные решения:

- добавить для QA-сборки аргумент запуска, отключающий подсказки, например `--disable-tooltips`;
- добавить стабильные идентификаторы самой подсказке и кнопке её закрытия, чтобы автотест мог обнаружить и закрыть её;
- сделать подсказку неблокирующей, чтобы нажатия вне самой подсказки передавались элементам основного экрана.

Предпочтительный вариант — аргумент запуска. По умолчанию подсказки остаются включёнными для ручного тестирования, а автотесты запускают приложение с отключёнными подсказками.

Если отключение подсказок реализовать нельзя, нужны стабильные идентификаторы для их обнаружения и закрытия.
